壹、目的與適用範圍

本工具用於規劃多點行程並產出公文格式的行程表。使用者貼上受訪單位名稱與地址、指定日期，系統自動完成分天、決定拜訪順序、安排午餐、配對高鐵車次，並輸出 Word 或 PDF。

適用於實地訪視、稽核、輔導、參訪等需要多點行程安排的作業。

系統會自動處理的事

  • 依地點座標分天，並在每一天內決定最短車程的拜訪順序
  • 避開受訪單位午休時段（預設 12:00–13:00），下午場次一律 13 時以後開始
  • 在適當時段插入午餐，依評分、價位、順路程度挑選餐廳
  • 依當日星期別配對有行駛的高鐵車次，去程與回程各留緩衝時間
  • 檢查是否超過目標結束時間，以及行程是否壓到午休

系統不會處理的事

  • 不會訂高鐵票、不會訂餐廳，僅提供建議
  • 車程為推估值，實際走過後請自行回填修正
  • 疏運期間（連續假期）的加班車不在班表內，需另行查詢
  • 受訪單位的聯絡與確認仍須人工進行

存取控制

前端網頁與程式碼儲存庫皆為公開，程式碼中不含任何金鑰。API 金鑰存放於 Apps Script 的指令碼屬性，通行碼由使用者自行輸入並僅存於個人瀏覽器。

通行碼是唯一的一道防線。Apps Script 必須部署為「任何人可存取」，靜態網頁才呼叫得到，因此網址等同公開。通行碼應使用 16 字元以上的隨機字串，不得寫入任何檔案或公開場合。

後台採用獨立帳密，與通行碼分離。通行碼發給全體使用者，取得工具即等同取得通行碼；後台可檢視全體使用者之使用紀錄與回饋內容，故不共用同一組認證。後台密碼以 SHA-256 雜湊存放於指令碼屬性，不保存明碼；登入後核發之憑證存於瀏覽器分頁，六小時失效，連續五次登入失敗鎖定十五分鐘。

肆、使用者操作程序

一、首次使用設定

  1. 開啟工具網址（由管理者提供）。
  2. 展開頁面中的「設定」區塊。
  3. 於「公文設定」填入自己的姓名，這會記入使用紀錄。
  4. 於「Google 服務」填入管理者提供的通行碼，按「測試連線」。
  5. 確認顯示三行皆為正常：試算表可讀寫、地址定位正常、午餐搜尋正常。

設定保存在這台電腦的瀏覽器中，同一台電腦不需重複輸入。更換電腦或清除瀏覽器資料後需重新設定。

不填通行碼也能使用，只是地址改用縣市層級粗略定位、午餐為「待訂」占位、臺北－左營以外的區間不提供車次建議。排程、微調、產出公文等功能不受影響。

二、規劃行程

  1. 於「行程日期」填入西元日期，星期與民國年會自動換算。每天可各自設定集合時間、集合地點、是否需要午餐，以及解散地點（預設同集合地點）。
  2. 於「行程地點」逐列填入名稱與地址，地址須含縣市。整批名單可自 Excel 複製後貼進任一格，系統會自動展開成多列。
  3. 確認「設定」中的排程規則（每站停留時間、午休時段、目標與最晚結束時間）符合本次需求。出席人員來自不同縣市時，於「高鐵班次」按「＋ 加車次」加開起訖組別。
  4. 按「規劃行程」。系統會顯示每天的行程站數與結束時間，並列出需注意事項。行程若無法在預設時間內完成，仍會全部排入，超時部分以紅色標示。

集合地點要寫得出縣市。只填「飯店」這類名稱無法定位，該日的來回車程會退回預設值。請寫成「◯◯飯店（高雄市苓雅區◯◯路◯號）」。

三、檢視與微調

  • 拖曳卡片可改變順序，亦可跨天拖曳；行動裝置請改用卡片上的上下箭頭與日期下拉選單
  • 名稱、地址、停留分鐘、每段車程分鐘數皆可直接修改，時間欄會即時重算
  • 修改過的車程會標示「手動」，可按「改回自動」還原
  • 壓到午休的卡片會顯示為紅色，上方時間帶亦會同步標紅
  • 某一天被排空時仍會顯示卡片，可將其他天的卡片拖入虛線區域
  • 每天下方提供「在 Google 地圖開啟這天的路線」，可交由駕駛導航

請特別確認標示「推估」的車程。推估值誤差約在十分鐘上下。實際走過後回填正確分鐘數，該路段之後就會沿用實際值，名單愈用愈準。

四、產出與存檔

功能說明
產生 Word 檔下載 .docx，中文標楷體、英文 Times New Roman，表格外框 1.5pt、內框 0.5pt
複製行程表複製後可直接貼入 Word，保留表格結構
列印 / 存成 PDF以 A4 公文格式排版，每日一頁
儲存案件存入資料庫並產生案件連結，可分享給同事開啟同一份行程繼續編輯

產生 Word 或列印時，系統會自動儲存一次案件。同一案件重複儲存為更新，不會產生重複紀錄。開啟他人分享的案件連結時，自己這邊也需先填入通行碼。

輸出檔名帶案件代號，格式為「文件標題_案件代號」，例如 115年度北區訪視計畫_jf20260902-a7b3k9.docx；列印時「另存為 PDF」的預設檔名亦同。文件版面不含案件代號，公文格式不受影響。對外行文前應自行移除檔名中的代號段落。未填通行碼時無案件代號，檔名僅有文件標題。

伍、管理者維護作業

一、新增使用者

將工具網址與通行碼提供給對方即可，無須建立帳號。通行碼外流時，至 Apps Script 的「專案設定 → 指令碼屬性」修改 ACCESS_KEY，即時生效，並重新通知全體使用者。

二、更新高鐵班表

  1. 自台灣高鐵官網下載最新之常態時刻表。
  2. 將時刻資料整理為「班表」分頁格式後匯入。
  3. 匯入時務必取消勾選「將文字轉換為數字、日期和公式」，否則 06:15 會被轉為時間值。
  4. 於「更新日期」欄填入核對日期，前端會顯示此日期供使用者判斷資料新舊。
欄位說明
方向南下或北上
車次例如 0205
行駛日空白代表每日行駛；有限制才填，0 為週日、1 至 6 為週一至週六
十二個站別欄位空白代表該站不停；08:26-08:28 為到站與開車；單一時間代表起站或終點站
更新日期核對日期，會顯示於前端

若已申請 TDX 運輸資料流通服務金鑰，可於指令碼屬性填入 TDX_CLIENT_ID 與 TDX_CLIENT_SECRET，執行 refreshTimetable() 自動更新，亦可設定每月觸發程序自動執行。

三、修改程式

修改 Code.gs 後必須重新部署，僅存檔不會生效。

請走「部署 → 管理部署作業 → 鉛筆圖示 → 版本：新版本 → 部署」，網址會沿用。若誤走「新增部署作業」會產生新網址，須回頭修改前端的 DEFAULT_GAS_URL。

僅修改指令碼屬性（MAPS_KEY、ACCESS_KEY 等）為即時生效，不需重新部署。修改前端 index.html 後上傳至儲存庫覆蓋即可，約一至兩分鐘後生效。

自 26.02 起後端使用雲端硬碟服務（存放回饋截圖）。由 26.01 以前的版本更新上來時，重新部署後首次執行會要求重新授權，須增加勾選雲端硬碟權限，屬正常程序。

五、處理使用者回饋

使用者於工具右下角「意見回饋」送出的內容，寫入試算表「回饋」分頁；所附截圖上傳至雲端硬碟「JourneyForge 回饋附件」資料夾，分頁內僅保存連結。分頁與資料夾均於首次使用時自動建立，無須事先設置。

欄位說明
收件編號系統流水編號，自 R-0001 起。不得手動刪除資料列，將導致編號重複
使用者 / 版本送出者自填姓名，以及當時的工具版號
分類 / 滿意度分類為六項：介面設計、輸出文件、排程與車次、資料及效能、許願池、其他，預設「其他」；滿意度為五級量表，得為空白
內容 / 附件回饋本文（上限 5000 字）與截圖連結，最多三張
環境版本、瀏覽器、視窗尺寸與當次行程規模。不含單位名稱、地址或出席名單，且使用者得取消附帶
狀態 / 處理備註預設「待處理」，由管理者更新處理進度

管理者應定期檢視本分頁，判斷是否升列為 FEEDBACK.md 之 FB-0xx 正式追蹤項目，並依「伍之一、版本與變更管理」之發版程序辦理。

回饋附件未開放共用連結，僅本服務帳號可存取。使用者截圖多含受訪單位名稱與地址，如需對外提供應個案處理。

四、金鑰與費用管理

  • API 限制：於憑證頁面將金鑰限制為 Geocoding API 與 Places API (New) 兩項
  • 應用程式限制維持「無」：呼叫來自 Apps Script 伺服器而非瀏覽器，設定網域限制反而會擋掉自己
  • 配額上限：於「API 和服務 → 配額與系統限制」將兩個 API 的每日請求上限各設為 200 次
  • 預算通知：於「帳單 → 預算與快訊」設定金額門檻通知

成本概況：地址定位每千次 5 美元、餐廳搜尋每千次 40 美元，均有每月免費額度。以本會用量加上查詢結果快取，實際費用趨近於零。

六、後台管理介面

後台網址為 admin.html，與工具同一站台，需另一組帳密登入。首次啟用時，於 Apps Script 編輯器執行一次 setAdmin('帳號','密碼')，執行後請將引數清空再存檔；日後更換密碼再執行一次即可。密碼長度不得少於十碼。

分頁用途
總覽期間內規劃次數、產出份數、活躍使用者、待處理回饋、近七日錯誤，及每日活動趨勢
使用分析依使用者、星期與時段拆解之使用情形
回饋管理回饋清單與狀態維護，可直接寫回試算表，並可匯出 FEEDBACK.md 片段
案件瀏覽檢索案件、閱讀 Markdown、複製案件連結
錯誤與健康前後端失敗紀錄（同訊息合併計次）與連線健康檢查
成本與配額API 呼叫次數、快取命中率與估算費用
資料維運各分頁列數、班表版本、指令碼屬性設定狀態、版本一致性、快取清理

快取清理僅適用於「地點快取」與「餐廳快取」。「回饋」與「使用紀錄」不得刪列——回饋之收件編號係以列數推算，刪列將導致編號重複；清理回饋資料應改寫狀態欄。

伍之一、版本與變更管理

本工具採地端版控：版本資訊與變更紀錄以檔案形式隨程式一起發布，不依賴任何外部服務。

一、版號規則

採「年份後兩碼．當年度流水號」，例如 26.01。跨年自 01 重新起算。僅使用者可感知之異動才進版號；上線後之緊急修正以 26.01a、26.01b 表示。

版號寫在 index.html 開頭的 APP_VERSION 常數，主畫面右上角的徽章即由此顯示，點擊可開啟版本公告。

二、三份版控文件

檔案對象內容
CHANGELOG.md開發與接手人員各版異動之檔案、函式、原因、效能數據與相容性註記
patch-notes.html使用者版本公告，僅敘述操作面差異，不出現程式名詞
FEEDBACK.md管理者使用回饋清單，每筆有編號、狀態與對應版本

三份文件以編號互相串接：FEEDBACK.md 的 FB-0xx → CHANGELOG.md 之版本條目 → patch-notes.html 之公告。

三、發版程序

  1. 登記：新回饋寫入 FEEDBACK.md，給予編號，狀態為「待評估」。
  2. 排版次：決定納入之版本，狀態改為「已排入 26.xx」。
  3. 修改：異動程式，並同步更新 guide.html、sop.html、README.md 之相關說明。
  4. 撰寫：更新 CHANGELOG.md、patch-notes.html，並將 APP_VERSION 跳號。
  5. 結案：FEEDBACK.md 狀態改為「已上線 26.xx」，經驗收後改為「已驗收」。

不採納之回饋亦應留存紀錄，狀態填「不採納」並敘明理由。此為本機制最主要之價值：避免同一事項於日後重複提出與重複評估。

陸、管考與統計

資料庫的「使用紀錄」分頁記錄每一次操作，可據以統計使用率與產出。

本分頁之寫入功能於 26.02 修復。26.01 以前前端雖有送出紀錄，後端並未建立對應處理程序，故無資料留存；管考統計應自 26.02 上線日起算。

欄位說明
時間動作發生時間
使用者使用者於設定中填入的姓名
動作規劃行程、儲存案件、產生Word、列印、開啟案件
案件ID對應「案件」分頁，可追查該次產出的完整內容
標題文件標題，通常為計畫名稱
天數 / 行程站數該次行程的規模

可產出的管考指標

  • 使用率：依「使用者」與「時間」樞紐分析，可得各人各月的使用次數
  • 產出量：篩選動作為「產生Word」或「列印」的紀錄，即為實際產出的公文份數
  • 規模統計：加總「行程站數」可得期間內規劃的停靠點總數
  • 完整內容追溯：以案件ID 至「案件」分頁查詢，Markdown 欄為可直接閱讀的完整行程

上列指標已於後台「總覽」與「使用分析」直接呈現，毋須自行製作樞紐分析；資料來源為同一份「使用紀錄」分頁。

「平均停留時間」無法自現有資料產出。「使用紀錄」記錄的是離散動作，並無一段使用的起迄時間；以同一使用者首末動作之時間差推算，將使「開啟後未再操作即關閉」之情形計為零，失真程度高於不予呈現。如確有需要，須於前端另行埋設起迄點，屬後續開發項目。

「使用者」為自行填寫的欄位，非經驗證的身分。用於內部管考足夠，但無法防止填寫不實。

「案件」分頁同時保存兩種格式：Markdown 供人閱讀與彙整報告，JSON 供系統還原為可編輯的行程。座標、停留時間、人工調整過的車程等資訊僅存於 JSON。

陸之一、後台監控項目

除使用統計外，後台另記錄兩類資料，均由程式自動寫入，分頁於第一次用到時自動建立。

分頁欄位用途
錯誤時間、使用者、版本、來源、動作、訊息、詳細、環境、狀態前端與後端之失敗紀錄。來源分為「前端」（未捕捉例外）、「後端」（Apps Script 回報之錯誤）、「排程」（有地點排不進去、超過最晚結束時間）
用量日期、geocode呼叫、geocode快取命中、places呼叫、places快取命中一日一列，供估算 API 費用與快取效益

錯誤紀錄於送出失敗時（未連線、未輸入通行碼、後端異常）暫存於使用者瀏覽器，待下次進站補送，避免失敗紀錄本身也一併遺失。同一則訊息於單次連線僅送出一次。

費用為依呼叫次數乘以單價之推算值，僅供趨勢判讀；實際帳單以 Google Cloud 計費頁面為準。目前帳單掛於個人信用卡，應併同「搬移至 Workspace 公用帳號」一案處理。
